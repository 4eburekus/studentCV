# Инструкция: БД, S3 и API

Как пользоваться поднятым окружением. Для разработки: сначала `docker compose up -d`
(см. `README.md`), дальше команды из этой инструкции.

# 1. База данных (PostgreSQL)

## Как попасть

| Способ | Как |
| --- | --- |
| pgAdmin (браузер) | http://127.0.0.1:5050, сервер `ksu-db` прописан сам |
| psql в контейнере | `docker compose exec db psql -U studentcv -d studentcv` |
| с хост-машины | `psql -h 127.0.0.1 -p 5433 -U studentcv -d studentcv` |

Порт наружу опубликован только как `127.0.0.1` — извне машины база не доступна.

## Правило №1: схему руками не менять

Структура таблиц задаётся моделями (`db/models.py`) и миграциями (`alembic/versions/`). Правка
таблиц через pgAdmin запрещена: `alembic revision --autogenerate` увидит расхождение и начнёт
генерировать обратные `DROP`, которые снесут чужую работу.

pgAdmin используется для **просмотра данных и выборок**.

```sql
\dt                                -- список таблиц
select * from students;            -- в SQL-окне pgAdmin (Queries -> Execute)
\d attendance_records              -- через psql
```

Кириллица в psql из-под Windows может отображаться неверно — это кодировка консоли, данные в базе
в порядке.

## Как изменить схему (единственный правильный путь)

```
# 1. поправить db/models.py
# 2. сгенерировать ревизию (нужен запущенный db)
docker compose run --rm backend alembic revision --autogenerate -m "что_добавили"
# 3. ОБЯЗАТЕЛЬНО открыть alembic/versions/<rev>_*.py и проверить:
#    - enum-тип не создаётся вручную (иначе DuplicateObjectError)
#    - имена CHECK без префикса ck_ (префикс добавляет naming_convention)
#    - server_default не потеряны
# 4. применить и проверить обратный ход
docker compose run --rm backend alembic upgrade head
docker compose run --rm backend alembic downgrade -1 && docker compose run --rm backend alembic upgrade head
# 5. контроль, что модель и миграция не разошлись
docker compose run --rm backend alembic check
```

Текущая схема: `0002_photo_storage (head)`.

## Демо-данные

```
docker compose run --rm backend python -m db.seeds
```

Создаёт преподавателя (`teacher` / `Teacher123!`), четырёх студентов, дисциплину и пары на
ближайшую неделю. Скрипт идемпотентен — можно запускать много раз, дублей не будет.
Эталонные фото сидами **не** создаются: это объекты в S3, см. §2.

# 2. Хранилище объектов (S3 — SeaweedFS)

## Что где лежит

| Бакет | Что | Ключ | Кто пишет |
| --- | --- | --- | --- |
| `biometrics` | эталонные фото студентов | `biometrics/<uuid4>.jpg` | только API (backend) |
| `frames` | доказательные кадры распознаваний | `frames/<lesson_id>/<uuid4>.jpg` | нативный CV-процесс |

В БД хранится **ключ**, а не картинка: `student_photos.photo_url`. Формат ключа закрепляющего
CHECK'ом — свой ключ записать в таблицу напрямую нельзя.

## Как попасть

| Способ | Как |
| --- | --- |
| aioboto3/boto3 | endpoint `http://storage:8333` (из контейнера backend), path-style; пример ниже |
| `weed shell` | `docker compose exec storage sh -c "printf 'fs.ls /\n' | weed shell -master=127.0.0.1:9333"` - в корне видны `buckets` и `topics` (проверено); в образе есть `weed` и `curl`, но **нет `mc`** |
| Браузерной консоли нет | содержимое бакетов - через `weed shell` или boto3; дамп и его проверка - `app/tools/storage_backup.py` |

Важно: у SeaweedFS нет веб-консоли, а `mc` (MinIO-клиент) в образ не входит - не ищите его,
как не искали бы `psql` в образе nginx. Живое содержимое бакета: `weed shell` или boto3.
`verify` в storage_backup проверяет дамп на диске, а не бакет.

Учётки в `.env`: `STORAGE_ADMIN_ACCESS_KEY`/`_SECRET_KEY` (полные права, для backend) и
`CV_ACCESS_KEY`/`CV_SECRET_KEY` (CV-процесс: пишет и читает только `frames`, в `biometrics` —
отказ).

Проверка, что хранилище живо и настроено:

```
curl -s http://127.0.0.1:8000/healthz
# {"status":"ok","database":"ok","storage":"ok","storage_warnings":[]}
```

`storage: "unconfigured"` — хранилище отвечает, но бакетов нет: перезапустите backend, он создаёт
их при старте сам. `"down"` — само хранилище не отвечает.

## Как положить и забрать объект

Штатный путь эталона — через API (`POST /students/{id}/photos`). Напрямую, для проверки
(cmd/PowerShell не понимают heredoc `<<PY`, поэтому скрипт в файле и pipe через `type`):

```
# сохраните как _s3.py и выполните из корня проекта:
#   type _s3.py | docker compose exec -T backend python -
import asyncio
from app.services import storage

async def main():
    key = storage.new_biometric_key()          # biometrics/<uuid4>.jpg - формат из CHECK
    await storage.put_object("biometrics", key, open("test.jpg", "rb").read())
    print("ok:", key)
    print("exists:", await storage.object_exists("biometrics", key))
asyncio.run(main())
```

`ensure_buckets()` (создание бакетов + версионирование) вызывать руками не нужно: он выполняется
при старте приложения.

## Бэкап: только парой

Ключи фото живут в БД, байты — в бакетах. Один дамп базы без дампа объектов даёт журнал со
ссылками в никуда.

```
powershell -ExecutionPolicy Bypass -File scripts\backup.ps1           # база
powershell -ExecutionPolicy Bypass -File scripts\backup_storage.ps1   # объекты
powershell -ExecutionPolicy Bypass -File scripts\restore.ps1          # база
powershell -ExecutionPolicy Bypass -File scripts\restore_storage.ps1  # объекты
powershell -ExecutionPolicy Bypass -File scripts\restore_storage.ps1 -VerifyOnly  # проверка дампа без записи
```

Проверка рассинхрона (что ни один ключ не указывает в пустоту):
`app.services.photos.verify_objects(session)` возвращает список ключей, которых нет в бакете.

# 3. API

Живёт на **http://127.0.0.1:8000**, документация — `/docs` (Swagger) и `/openapi.json`.

## Авторизация — сейчас заглушка

Все пути `/api/v1/*` требуют заголовок `Authorization: Bearer <что угодно>`. Проверяется
**наличие** заголовка, подлинность токена — нет (требование №11 закрыто частично, реальный вход —
отдельный срез). Без заголовка — `401`. `/healthz` доступен без авторизации.

```
curl -s http://127.0.0.1:8000/api/v1/students -H "Authorization: Bearer dev"
```

## Методы

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/healthz` | готовность (бд + хранилище) |
| POST | `/api/v1/students` | завести студента (ФИО + группа) |
| GET | `/api/v1/students?group=&q=&is_active=&page=&limit=` | список с фильтрами |
| GET | `/api/v1/students/{id}` | один студент |
| PATCH | `/api/v1/students/{id}` | правка ФИО/группы/активности |
| DELETE | `/api/v1/students/{id}` | **мягкое** удаление (`is_active=false`), журнал сохраняется |
| POST | `/api/v1/students/{id}/photos` | загрузить эталон (multipart, jpeg/png) |
| GET | `/api/v1/students/{id}/photos` | список эталонов + статус 1–5 |
| DELETE | `/api/v1/photos/{id}` | удалить строку **и** объект |
| GET | `/api/v1/lessons?discipline_id=&date=&page=&limit=` | пары (только чтение) |
| POST | `/api/v1/attendance/events` | приём события распознавания |
| GET | `/api/v1/attendance/journal?lesson_id=` | журнал пары |

## Примеры

Создать студента (формат группы — ровно 2 цифры, 3–4 заглавных, 0–3 строчных, 2 цифры).
С кириллицей из Windows надёжнее отдавать тело файлом в UTF-8, а не в командной строке
(создание через inline `-d` с русским текстом зависит от кодовой страницы консоли):

```
# body.json (UTF-8): {"full_name": "Иванов Иван Иванович", "group_number": "01-ФИИтт-01"}
curl -s -X POST http://127.0.0.1:8000/api/v1/students \
  -H "Authorization: Bearer dev" -H "Content-Type: application/json" \
  --data @body.json
```

Без кириллицы в теле inline-`-d` работает как обычно. GET с заголовком — работает всегда.

Загрузить эталон:

```
curl -s -X POST http://127.0.0.1:8000/api/v1/students/1/photos \
  -H "Authorization: Bearer dev" -F "file=@photo.jpg"
```

Событие распознавания:

```
curl -s -X POST http://127.0.0.1:8000/api/v1/attendance/events \
  -H "Authorization: Bearer dev" -H "Content-Type: application/json" \
  -d "{\"lesson_id\": 1, \"student_id\": 1, \"captured_at\": \"2026-11-16T08:37:00+00:00\", \"frame_object_key\": \"frames/1/6f1c...jpg\"}"
```

Ответ: `{"record": {...}, "outcome": "recorded", "lesson_start": "08:30", "delay_minutes": 7}`.

Проверенные способы отправки **кириллицы** из Windows: curl с заголовком работает, но `-d` с
русским текстом прямо в командной строке зависит от кодовой страницы консоли — надёжнее
`--data @body.json` (файл в UTF-8, проверено: студент с русским ФИО создаётся без искажений)
или PowerShell `Invoke-WebRequest` (тоже проверено, 201).

## Правила, которые применяет API (важно для ожидания от ответа)

- раньше начала пары → `PRESENT`, `delay_minutes: null`
- ровно в начало → `LATE`, `delay_minutes: 0`
- позже начала, но раньше конца → `LATE`, минуты округляются вверх
- **не раньше конца пары → запись не создаётся**: ответ `200`, `record: null`,
  `outcome: "ignored_after_lesson_end"`. Это не ошибка
- повтор по той же паре → побеждает **самый ранний** вход (`kept_earlier_entry`)
- запись, исправленную руками, автоматическое событие не меняет (`kept_manual_edit`)

Исход всегда читается из поля `outcome`, а не из кода ответа: `201` — создали или обновили,
`200` — не изменили (по любому из трёх оснований).

# Памятка: frontend-разработчик

1. **Источник истины — OpenAPI, а не эта таблица**: http://127.0.0.1:8000/openapi.json (Swagger UI
   на `/docs`). Поля, обязательность и коды ответов берутся оттуда; срез схемы обновляет спеку
   автоматически.
2. **Заголовок `Authorization: Bearer <token>` обязателен** на всех `/api/v1/*`. Сейчас содержимое
   токена не проверяется (заглушка), но заголовок нужен: без него `401` с `WWW-Authenticate`.
   Клиент обязан обрабатывать 401 с первого дня — срез реального входа появится позже и не изменит
   пути.
3. **Пути — `/api/v1/...`**. Версия в префиксе, не в теле. Не завязывайтесь на порядок полей JSON и
   на русские тексты в `detail` — сообщения меняются, коды и enum'ы нет.
4. **Данные о посещаемости читаются через `outcome` и `record`**:
   - `outcome: "recorded"` → запись создана/обновлена;
   - `"kept_earlier_entry"` / `"kept_manual_edit"` → ничего не изменилось;
   - `"ignored_after_lesson_end"` → `record: null`, студент по паре считается не пришедшим.
   Код `200` vs `201` различает «изменили» / «не изменили», но подробность — только в `outcome`.
5. **`ABSENT` нет в данных как статус.** Отсутствие студента в `GET /attendance/journal` = не пришёл.
   Отличить «не пришёл» от «пришёл после конца пары» по API нельзя (известный открытый вопрос).
6. **Фото**: загрузка — `multipart/form-data` c полем `file`, принимаются только jpeg/png (иначе
   `415`), максимум 5 (иначе `422` со структурированным `detail`: `photos_total`, `max_photos`).
   В списке эталонов смотрите `status`: `"below_minimum"` — эталонов меньше `min_photos`, студент
   не распознаётся; показывать это надо, удаление последнего эталона разрешено.
7. **`photo_url` — ключ объекта, а не ссылка для `<img src>`**. Прямой доступа к бакету нет,
   presigned-выдача ещё не реализована (ждёт решения о топологии). Для превью нужен будет либо
   отдельный эндпоинт отдачи, либо срез presigned.
8. **Пагинация**: `page` (с 1) + `limit` (1–500, по умолчанию 50); в ответе есть `total`.
   Фильтры студентов: `group` (точное совпадение), `q` (подстрока ФИО/группы), `is_active`
   (по умолчанию только активные).
9. **Ошибки**: `401` нет заголовка, `404` объекта нет, `409` конфликт состояния, `415` тип файла,
   `422` данные не подходят, `503` база или хранилище не отвечают. Тело везде
   `{"detail": ...}` — строка или объект (у `422` бывает список ошибок валидации).
10. **`DELETE /students/{id}` — мягкое**: студент останется в базе с `is_active=false`, в списке по
    умолчанию его не будет. Физического удаления из UI не делать.
11. **Даты пар**: у журнала есть `lesson_date`, `start_time`, `end_time` — опираться на них, а не на
    «сегодня», иначе тесты на границах пары будут врать (даты пар в сидах — на ближайший
    понедельник).
12. **Локальный запуск dev-агента**: `docker compose up -d` (backend стартует сам с
    `--reload`), API на `8000`, S3 на `8333`. Не поднимайте второй uvicorn — порт занят.

# Памятка: разработчик CV-модуля

1. **Вы — клиент двух сервисов, оба по loopback с хост-машины:**
   - S3: `http://127.0.0.1:8333` (path-style, SigV4 работает как с настоящим AWS);
   - API: `http://127.0.0.1:8000/api/v1` + `Authorization: Bearer <что угодно, наличие обязательно>`.
   Локальная сеть compose (`http://storage:8333`, `http://db:5432`) от вас **не** видна.
2. **Креды и права — только из `.env`:** `CV_ACCESS_KEY` / `CV_SECRET_KEY`. Это сервисная учётка, у
   неё есть право писать и читать **только `frames`**. В `biometrics` она получает `AccessDenied` —
   это не баг и не надо просить админские ключи: эталоны читает backend.
3. **Ключ файла — контракт, он проверяется.** Шаблон кадра: `frames/<lesson_id>/<uuid4>.jpg`
   (дефисы в uuid обязательны, нижний регистр). Не соответствующий формат API отвергает
   `422` с текстом про format — искать проблему надо в своём коде, а не в бакете. Для генерации
   convenient-путь: `app.services.storage.new_frame_key(lesson_id)`.
4. **Порядок действий на событие — сначала файл, потом событие.** Запилили кадр в `frames` →
   `POST /attendance/events` с `frame_object_key` этого кадра. Если объекта в бакете нет, API
   ответит `422` («кадра нет») и запись не создаст: кадр — доказательство отметки.
5. **`captured_at` — с временной зоной** (timestamptz, ISO8601), и это время прохода человека, а не
   время отправки. Наивное время примут и посчитают UTC — лучше не передавать без зоны. Границы
   пары считаются от даты **пары**, а не от дня события: событие не в свой день не будет
   записано.
6. **`student_id` / `lesson_id` берите из API, а не из своего кэша:**
   - `GET /api/v1/lessons?date=&discipline_id=` — `id`, `lesson_date`, `start_time`, `end_time`
     (последние два нужны, чтобы понять, опоздание это или уже поздно);
   - студентов ищите через `GET /api/v1/students?group=` / `?q=`; студент с `is_active=false` даёт
     `409` на событие.
7. **Не бойтесь повторной доставки.** Отправленное дважды одно и то же событие не создаёт дубль:
   `UNIQUE (student_id, lesson_id)` + «побеждает самый ранний вход». Повтор с более поздним временем
   вернёт `200` / `outcome: "kept_earlier_entry"` — это успех, а не ошибка. Ретраи по таймауту
   безопасны. Отдельный `is_manually_edited`-статус (`kept_manual_edit`) означает: журнал по этой
   паре правил преподаватель, ваше событие сознательно отброшено.
8. **Не пытайтесь «починить» статус на своей стороне.** `PRESENT/LATE/ABSENT`, минуты опоздания и
   отбрасывание событий после конца пары считает backend. Прислать более раннее время — законный
   способ улучшить отметку студента (оно и победит), прислать «PRESENT вручную» — невозможно: поля
   статуса в запросе нет.
9. **Эталоны (`biometrics`) не трогаем.** Не читаем, не пишем, не удаляем: у вашей учётки нет прав,
   и это осознанно. Очередь распознаваний, которую поднимет срез Celery+Redis, будет получать
   эталоны через backend, а не напрямую из бакета.
10. **Что упадёт и почему, по кодам:** `401` — забыли заголовок; `404` — нет такой пары; `409` —
    студент неактивен; `422` — неверный формат ключа кадра / нет файла в `frames`; `503` — хранилище
    недоступно (это проблема окружения, повторяйте позже — данные при этом не потеряны).
11. **Проверка окружения перед отладкой:** `curl http://127.0.0.1:8000/healthz` →
    `"storage":"ok"`. `unconfigured` — бакеты не созданы, перезапустите backend; `down` — хранилище
    не отвечает.
12. **Версионирование включено:** перезапись объекта с тем же ключом не уничтожает предыдущую
    версию. Но ключи обязаны быть уникальными uuid — не переиспользуйте имя файла для разных
    событий.
