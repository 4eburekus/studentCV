## 1. Рамки среза

**Входит:**

1. `compose.yaml` с сервисами `db` (PostgreSQL) и `pgadmin4`.
2. Python-окружение в контейнере для запуска Alembic и сидов (FastAPI в этот срез не входит).
3. `db/models.py` — 6 таблиц строго по схеме из README.
4. Alembic: async-обвязка, первая миграция `0001_init`, прогон туда/обратно.
5. Сиды: преподаватель, студенты с корректными номерами групп, дисциплина, пары по шаблону расписания.

**Не входит (следующие слои):** Redis + Celery, CV/InsightFace-модуль, реальный вход
(требование №11 закрыто заглушкой), ручное редактирование журнала, отчёты, интеграция с
ЕИОС, инсталлятор поставки.

**Закрыто сверх первоначального списка этого раздела:** объектное хранилище (§1.2, реализовано на
SeaweedFS вместо MinIO), загрузка эталонных фото и правило 1–5, CRUD студентов и приёмник
событий посещаемости (§3.9), заглушка авторизации.

**Зафиксированные решения:**

| Вопрос | Решение |
| --- | --- |
| Режим ORM | SQLAlchemy 2.0 **async**, драйвер `asyncpg`. ДSN: `postgresql+asyncpg://…` |
| Объём «готово» | Только БД: compose + модели + Alembic + сиды |
| Справочник времени пар | **Отложено**, см. §9 «Открытые вопросы». Схема `lessons` — точно как в README |
| Противоречие «локальный десктоп» vs Docker | **Снято гибридом**: состояние — в контейнерах, CV-инференс — нативным процессом Windows. См. §1.1 |
| Формат поставки (AC1) | **Переформулирован** и внесён в `Реестр требований.md`: фиксируется автономность и один запуск установщика, а не формат архива |

### 1.1 Гибридная развёртка: границы контейнеров и нативного процесса

Требование №10 («локальное десктопное исполнение под Windows, всё на ПК пользователя») не
противоречит Docker, если делить слои по владению ресурсами, а не по принципу «всё или ничего».

| Слой | Где живёт | Почему именно так |
| --- | --- | --- |
| PostgreSQL, Redis, объектное хранилище (SeaweedFS) | контейнеры compose | состояние, переносимость, бэкап, отсутствие ручной установки СУБД у пользователя |
| Backend FastAPI + Celery | контейнеры compose | чистые Python-зависимости, воспроизводимость сборки |
| CV-инференс (PyTorch/InsightFace + OpenCV-захват камеры) | **нативный процесс Windows** | проброс GPU в WSL2 требует NVIDIA Container Toolkit и даёт хрупкую связку драйвер ↔ toolkit ↔ образ; захват камеры с Windows-устройства из Linux-контейнера — отдельный класс проблем; 4 ГБ VRAM (RTX 3050 Laptop) не хочется делить через слой виртуализации |
| pgAdmin 4 | **только dev-таргет** | инструментарий разработки, в поставку не входит |

Связь «нативный CV-процесс → состояние» идёт через те же контракты, что и контейнерный backend:
**Celery-задачи через Redis** и **фото через S3-совместимый API** (SeaweedFS, generic S3). CV-процессу
достаточно переменных `REDIS_URL`, `DATABASE_URL`, `S3_*` в окружении — он не «знает», что окружение
смешанное. Единственный дополнительный шаг при его установке — `pip install asyncpg` без Docker.

**Один compose, два таргета.** Структура вводится сразу — менять её после появления фронта дорого:

- `compose.yaml` — ядро: `db` и `storage` (**без секции `ports:` вообще**), `migrate` (одноразовый,
  `profiles: ["ops"]`), volumes, сеть, `env_file: .env`, `restart: unless-stopped`.
- `compose.override.yaml` — dev, подхватывается автоматически: проброс `127.0.0.1:5433:5432` и
  `127.0.0.1:8333:8333`, сервис `pgadmin4` + его volume, `backend` с uvicorn и `--reload`,
  bind-mount исходников `app/`, `db/`, `alembic/`, `tests/` и каталога `./backups:/backups`.
- `compose.dist.yaml` — поставка: pgAdmin исключается через `!reset null`, у `db` сбрасываются
  порты и bind-mount'ы, `backend` становится службой на `127.0.0.1:8000`, `AUTH_STUB_ENABLED`
  принудительно `false`; образы пинняются по digest; `caddy` для Vite-фронта — заготовка-комментарий.

**Порт S3 наружу — первое осознанное исключение** из принципа «наружу только порт приложения»
(согласовано 10.11.2026): нативный CV-процесс живёт вне сети `studentcv-net` и ходит в хранилище по
`127.0.0.1:8333`. Привязка к loopback сохраняет требование №11 — извне машины доступ закрыт.
Internal-порты weed (9333 master, 8888 filer) не публикуются ни в одном таргете.

### 1.2 Объектное хранилище: почему SeaweedFS, а не MinIO

План предполагал MinIO. Реализация ушла на **SeaweedFS** по причине, которую не обойти конфигом:
официальные образы MinIO из этой среды не загружаются — Docker Hub отвечает `pull access denied` на
любые теги `minio/minio` (включая ранее публичные), `quay.io/minio/*` — `401`, `dl.min.io` — таймаут.
При этом `postgres` и `busybox` тянутся нормально, то есть блокировка точечная по репозиториям MinIO,
а не сетевая.

| Критерий | MinIO | SeaweedFS (взято) |
| --- | --- | --- |
| доступность образа | нет из нашей среды | есть, публично |
| лицензия | AGPL-3.0 (+ коммерческая модель) | Apache-2.0 — без вопросов для вуза |
| S3-совместимость | эталон де-факто | generic S3: SigV4, path-style |
| versioning | есть | есть, **с 4.49** (на 3.83 — `NotImplemented`) |
| учётные записи | `MINIO_ROOT_*` + `mc admin` | декларативный `s3.json` (init-контейнер не нужен) |
| веб-консоль | :9001 | нет (администрирование через `weed shell`) |

Принятые осознанно риски: семантика отдельных S3-операций может отличаться — поэтому всё
взаимодействие с хранилищем вынесено в `app/services/storage.py` (единственная точка), а инструмент
бэкапа работает по generic S3 и переживёт возврат на MinIO. Пиннинг версии обязателен: `4.53`
зафиксирован как минимально рабочая для versioning'а.

Правило: `docker compose up -d` в dev не должен требовать флагов; поставка запускается явно
`-f compose.yaml -f compose.dist.yaml`.

**Поставка «как .exe»** (описываем сейчас, реализуем в срезе поставки). Инсталлятор (Inno Setup/WiX):
проверка WSL2 и виртуализации → установка runtime → `docker load` из **tar-архива образов,
приложенного к дистрибутиву** (выход к Docker Hub в контуре КГУ скорее всего закрыт, тянуть на месте
нельзя) → ярлык. Запускатор-`.exe` выполняет
`docker compose -f compose.yaml -f compose.dist.yaml up -d`, ждёт healthy-статус и открывает
`http://127.0.0.1:8000`. Пользователь видит десктопное приложение, «всё локально» соблюдено, а
compose остаётся деталью реализации.

**Лицензия.** Docker Desktop для образования и некоммерческого использования идёт по Personal-тарифу,
но эксплуатация на ПК университета как внутренней ИТ-инфраструктуры требует юридической проверки, а не
предположения. Free-путь: Docker Engine или **Podman** (Apache-2.0, читает compose-файлы) внутри WSL2 —
compose-артефакты от этого не меняются, и это ещё один аргумент описывать инфраструктуру именно в
compose, а не скриптами установки.

**Что compose не убирает** (оставается зоной риска, см. §8):

- Требование админ-прав, включённой виртуализации и WSL2 на хосте — в управляемом образе ПК КГУ это
  не всегда проходимо, нужен либо заранее согласованный образ, либо fallback на нативный установщик.
- `pgdata` в volume не переносится копированием папки → бэкап становится отдельным требованием среза
  (§3.8), иначе один `down -v` на чужом ПК уничтожает журнал.
- Docker Desktop + WSL2 + PostgreSQL + Redis + CV-модель на одном ноутбуке — 8–16 ГБ RAM; сверить с
  ТЗ на подбираемое оборудование (веха 4).

### 2.1 Сервисы

| Сервис | Файл | Образ | Порт наружу | Примечание |
| --- | --- | --- | --- | --- |
| `db` | `compose.yaml` | `postgres:16-alpine` | нет (в override — `127.0.0.1:5433:5432`) | volume `pgdata:/var/lib/postgresql/data`; init-скрипты в `/docker-entrypoint-initdb.d` |
| `migrate` | `compose.yaml` | сборка `docker/backend.Dockerfile` | — | одноразовый, `profiles: ["ops"]`, `command: alembic upgrade head`, `restart: "no"`, `depends_on` db healthy |
| `pgadmin4` | `compose.override.yaml` | `dpage/pgadmin4:8` | `127.0.0.1:5050:80` | volume `pgadmin_data`; монтируется `servers.json`; в dist исключён через `!reset null` |
| `backend` | `compose.override.yaml` | сборка `docker/backend.Dockerfile` | — | `profiles: ["tools"]`, bind-mount `db/`, `alembic/`, `alembic.ini`; в этом срезе только инструмент для Alembic/сидов |

В `compose.yaml` у `db` **нет секции `ports:`** — наружу БД не публикуется вообще. Проброс появляется
только в dev-override и исчезает в dist, поэтому прод-развёртка по умолчанию безопаснее dev, а не
наоборот.

### 2.2 Обязательные детали

- **Healthcheck на `db`** — `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB`, интервал 5s, retries 10.
  `pgadmin4` и `backend` идут через `depends_on: {db: {condition: service_healthy}}`, иначе pgAdmin
  стартует с мёртвым сервером, а Alembic падает на first-connect.
- **Именованные volumes, а не bind-mount** для `pgdata` — на Windows bind-mount на data-каталог PG
  даёт проблемы с правами и падение кластера.
- **Порт 5433 вместо 5432** — на хосте Windows скорее всего стоит локальный PostgreSQL; требование
  №11 (доступ только у авторизованного преподавателя) также требует привязки к `127.0.0.1`, чтобы
  БД не слушала наружу. Перед стартом: `netstat -ano | findstr ":5433 :5050"`.
- **Контейнерный Python — 3.12-slim.** README задаёт нижнюю границу «3.10+», хостовой Python на машине
  — 3.13.14. 3.12 берём как самый безопасный общий знаменатель для `asyncpg` и будущих PyTorch/CUDA
  сборок, которые придут в CV-слое.
- **Сеть** `studentcv-net`; внутри неё backend видит БД как `db:5432`, pgAdmin — так же.
- **Пароли только из `.env`**. В репозитории — `.env.example`. `servers.json` содержит пароль в
  открытом виде (ограничение формата pgAdmin) — это допустимо только для dev-контура и фиксируется
  в §9 как вопрос для КГУ.
- **`PGADMIN_CONFIG_MASTER_PASSWORD_REQUIRED=False`** + `PGADMIN_CONFIG_SERVER_MODE=False`, иначе
  pgAdmin требует мастер-пароль и не показывает прописанный сервер без входа.

### 2.3 Переменные

```
POSTGRES_USER=studentcv
POSTGRES_PASSWORD=***            # из .env, для dev — любой не-пустой
POSTGRES_DB=studentcv
DATABASE_URL=postgresql+asyncpg://studentcv:***@db:5432/studentcv
PGADMIN_DEFAULT_EMAIL=dev@ksu.local
PGADMIN_DEFAULT_PASSWORD=***
```

Отдельно: `DATABASE_URL_SYNC` (`postgresql+psycopg://…`) **не заводим** — см. §5, Alembic работает
через async-engine.

## 3. Модель данных

Таблицы — 1:1 с README. Ниже то, что в README не записано, но прямо следует из требований; это надо
принять как решение слоя, иначе потом придётся править схему миграцией под живыми данными.

**Общее:**

- `naming_convention` в `Base.metadata` (`ix`, `uq`, `fk`, `pk`, `ck`) — имена ограничений предсказуемы
  в миграциях и в `pgadmin`, а не `pg_delta_…`/`attendance_records_delay_minutes_check`.
- Тип PK: `Integer` (по README). Переход на `BigInteger`/`identity` — вопрос на будущее, сейчас не
  блокирует.
- `created_at` / `updated_at` через `server_default=func.now()` и `onupdate`.
- Время: `entry_time`, `created_at`, `edited_at` — `timestamptz` (не naive `DateTime`), иначе
  расчёт опоздания поплывёт при переносе сервера/смены TZ. `lesson_date` — `Date`,
  `start_time`/`end_time` — `Time`.

**3.1 `teachers`** (треб. №11)

`id`, `full_name`, `login` (UNIQUE, NOT NULL), `password_hash` (NOT NULL).
В сидах — тестовый преподаватель с `password_hash = bcrypt("dev")`, чтобы следующий слой авторизации
имел валидный хэш, а не заглушку.

**3.2 `students`** (треб. №9)

`id`, `full_name` (NOT NULL), `group_number` (NOT NULL), `is_active` (Boolean, default true, server_default
`true`). Плюс:

- CHECK по регулярке: `group_number ~ '^\d{2}-[А-ЯЁ]{3,4}[а-яё]{0,3}-\d{2}$'` - формат
  `99-АААаа-99`: 3-4 заглавных, 0-3 строчных, номер курса двумя цифрами. Зафиксирован
  решением от 08.11.2026. Формат из README (`{2}` заглавных, одна цифра в конце) отброшен:
  реальные номера групп КГУ под него не подходили, README приведён в соответствие.
  Длины заданы диапазоном, а не точным числом: в КГУ встречаются и `ФИИтт` (3 заглавных
  + 2 строчных), и `ТИПП` (4 заглавных + 0 строчных).
  **Риск кириллического диапазона:** `[А-Я]` зависит от collation БД. Кластер создаём с
  `POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"` и в CHECK явно перечисляем `Ё` и `ё`.
  Отдельный тест: `01-ФИИтт-01` должен проходить, `01-фиитт-01` и `01-ФИтт-01` - не проходить.
  Если на `locale=C` заглавный диапазон не схлопывается, решаем расширенным классом
  символов, а не ослаблением проверки.
- Индекс `ix_students_group_number` (фильтрация по группам, требование №9/отчёты) и частичный
  `WHERE is_active` (основной выбор — активные).
- `full_name` без нормализации — пока как в README.

**3.3 `student_photos`** (треб. №8)

`id`, `student_id` FK → `students.id` **`ON DELETE CASCADE`**, `photo_url` (NOT NULL, UNIQUE — один путь
не может быть привязан дважды), `created_at`.
Ограничение «от 1 до 5» CHECK'ом по чужим строкам не выражается → реализуется в сервисном методе
(`count` перед вставкой) + опциональный триггер-страховка на уровне БД. В этот срез входит только
место под него (поле + комментарий в коде), сервис — следующий слой.

**3.4 `disciplines`** (треб. №6 «один журнал — одна дисциплина»)

`id`, `name` (NOT NULL), `teacher_id` FK → `teachers.id` (ON DELETE RESTRICT — журнал не должен
исчезать вместе с преподавателем).

**3.5 `lessons`** (треб. №5)

`id`, `discipline_id` FK, `lesson_date` (Date, NOT NULL), `start_time`/`end_time` (Time, NOT NULL) —
точно по README, справочник слотов отложен (§9).
CHECK `end_time > start_time`. Индекс `ix_lessons_discipline_date (discipline_id, lesson_date)` —
главный запрос слоя: «пара по дисциплине на сегодня/час».
UNIQUE `(discipline_id, lesson_date, start_time)` — защита от дубля пары (критерий Устава
«без потерь и дублей»).

**3.6 `attendance_records`** (треб. №4, №5, №7)

`id`, `student_id` FK, `lesson_id` FK, `entry_time` (timestamptz, NOT NULL), `status`
(native PG enum `attendance_status`: `PRESENT` / `LATE` / `ABSENT`), `delay_minutes` (Integer,
nullable), `is_manually_edited` (Boolean, default false), `edited_at` (nullable).

- **`UNIQUE (student_id, lesson_id)`** — самое важное дополнение. Одна запись на пару на студента;
  повторная доставка от Celery/камеры не создаёт дубль, а делает upsert. Без него критерий
  «95% передаются без потерь и дублей» невыполним на уровне данных.
- CHECK: `status = 'LATE'` ⇔ `delay_minutes IS NOT NULL`; `delay_minutes >= 0`.
  (Статус `ABSENT` без `entry_time` не допускается в этой модели: `entry_time NOT NULL` — запись
  создаётся по факту распознавания; absence формируется отсутствием строки. Если слой отчётов
  потребует явные строки `ABSENT`, это отдельная миграция и вопрос §9.)
- `status` — `sa.Enum(AttendanceStatus, native_enum=True, name="attendance_status",
  values_callable=lambda e: [m.name for m in e])`, чтобы в БД лежали `PRESENT/LATE/ABSENT`.
- Индексы: `lesson_id` (журнал пары), `student_id` (история студента), `entry_time`.
- `is_manually_edited`/`edited_at` пишутся **только** из ручного контура (треб. №7) — автоматический
  путь обязан оставлять их `false/NULL`.

**3.7 Сиды и расписание**

Сиды генерируют пары по шаблону README (7 слотов: 8:30–10:00, 10:10–11:40, 11:50–13:20, 14:00–15:30,
15:40–17:10, 17:20–18:50, 19:00–20:30) на ближайшую учебную неделю — этого хватает, чтобы видеть
осмысленные данные в pgAdmin и позже проверять расчёт опозданий.

**3.8 Бэкап и восстановление**

`pgdata` — именованный volume: он не переносится копированием папки, а `docker compose down -v`
на чужом ПК уничтожает журнал безвозвратно. Поэтому бэкап — не «на будущее», а часть среза.

- `scripts/backup.ps1` — `pg_dump -Fc` (кастомный формат, сжатие, восстановление через `pg_restore`)
  в `./backups/<timestamp>.dump`, ротация: хранятся 10 последних дампов. Скрипт **строго ASCII** —
  кириллица в `.ps1` ломает парсинг на этой машине.
- `scripts/restore.ps1` — восстановление из дампа в чистую БД: `pg_restore --clean --if-exists`.
- `scripts/smoke.ps1` — прогон проверок §7.6 (группы, статусы, уникальность, каскад).
- Вынос дампа делается через `docker compose exec -T db pg_dump ... > file`, чтобы не зависеть от
  `docker cp` и Windows-прав на внутренние файлы контейнера.
- Проверка на реальном дампе обязательна: снять дамп → `down -v` → `up` → восстановить → сверить
  количество строк. Бэкап, который ни разу не восстанавливали, — это гипотеза, а не бэкап.

**3.9 Классификация прохода (договорённость 10.11.2026)**

Реализация: `app/services/attendance.py::classify()` и `register()`. Границы считаются от
`lesson_date` + `start_time`/`end_time`, а НЕ от дня события.

| Случай | Исход | `delay_minutes` |
| --- | --- | --- |
| раньше начала пары | `PRESENT` | NULL |
| ровно в начало пары | `LATE` | 0 |
| позже начала, но раньше конца | `LATE` | ceil(минут), минимум 1 |
| не раньше конца пары | **строка не создаётся** → студент остаётся `ABSENT` | — |
| повтор по той же паре | побеждает **самый ранний** `entry_time` | — |
| запись с `is_manually_edited = true` | автоматическим событием **не трогается** | — |

Почему так, а не иначе:

- **«ровно в начало» = LATE с 0** — против прежней формулировки требования №5 (условие 4).
  Решение команды от 10.11.2026, реестр приведён в соответствие там же. Существующий CHECK
  `(status = 'LATE') = (delay_minutes IS NOT NULL)` и `delay_minutes >= 0` это допускает,
  поэтому **миграция не понадобилась** — изменение осталось в сервисном слое.
- **границы от даты пары** — регресс на реальный баг: `calculate_delay` строила start/end из
  `captured_at.date()`, поэтому пересланное вчера событие сравнивалось с парой того же дня,
  которой не было, и молча получало `LATE 30`.
- **ранний вход побеждает** — за один проход камера выдаёт десятки событий; если бы побеждало
  последнее, порядок доставки стал бы частью бухгалтерии, а сеть и ретраи порядка не гарантируют.
- **приоритет ручной правки над ранним входом** (требование №7): два условия собраны в одном
  `ON CONFLICT DO UPDATE ... WHERE` через `AND`.
- **«после конца пары» не записываем** — иначе журнал получал бы `LATE` на 300+ минут.
  Это не ошибка: событие валидно и сознательно не учитывается, поэтому ответ `200` с
  `record: null`, а не `4xx`.
- **исходы машиночитаемы**: `recorded` / `kept_earlier_entry` / `kept_manual_edit` /
  `ignored_after_lesson_end` — не `created: bool` (три разных «не изменилось» булев флаг не
  выражает) и не текст (формулировку меняют, контракт — нет).
- **`populate_existing` обязателен** при перечитывании записи после upsert: с
  `expire_on_commit=False` и `lazy="selectin"` обычный `session.get()` возвращает объект из
  identity map со СТАРЫМИ значениями, и API отвечал бы тем, чего в базе нет. Это был реальный
  баг, найденный прогоном, а не предположение.

Не закрыто и сознательно оставлено: **неразличимость «не пришёл» и «пришёл после конца»** в
данных журнала (оба случая — отсутствие строки). См. §9.

## 5. Alembic

1. `docker compose run --rm backend alembic init alembic` (создаём внутри образа, чтобы путь к коду
   совпадал с рантаймом).
2. `alembic.ini`: `sqlalchemy.url =` оставляем пустым; значение подтягиваем из `os.getenv("DATABASE_URL")`
   в `env.py` — пароли не должны попадать в трекаемый ini.
3. `env.py` — async-вариант: `engine_from_config`/`create_async_engine` +
   `connectable.run_async(do_run_migrations)`; `target_metadata = db.base.Base.metadata`;
   `render_as_batch=False` (PG умеет ALTER без re-create table).
4. `alembic revision --autogenerate -m "init"` → `0001_init`. **Ручная досмотрка обязательна:**
   autogenerate стабильно недогенерит native enum, CHECK-констрейнты и `server_default`.
   По enum: тип создаёт хук `before_create` при `create_type=True` — **вручную `create()` не
   зовём**, иначе `DuplicateObjectError` (проверено прогоном, см. §8).
5. Правило команды: схема меняется **только** моделью + миграцией. Правки таблиц руками в pgAdmin
   запрещены — иначе `--autogenerate` начинает генерить «обратные» DROP'ы и сносит чужую работу.
   pgAdmin используется как инструмент просмотра данных и SQL-консоль для выборок.
6. Прогон: `docker compose run --rm backend alembic upgrade head`, затем
   `downgrade base` → `upgrade head` обязан пройти чисто. Это критерий приёмки, а не «потом».
7. `docker compose up -d` в production-виде позже должен выполнять миграции перед приложением
   (сервис `migrate` с `depends_on: db healthy`, `command: alembic upgrade head`,
   `restart: "no"`). В этом срезе — только через `run --rm`.

## 7. Критерии приёмки (проверяемые руками)

1. `docker compose up -d` → `docker compose ps` показывает `db`, `storage` и `pgadmin4` как
   `healthy` (storage — по 403 на S3-эндпоинте: порт занят, кредов нет).
2. `docker compose exec db pg_isready -U studentcv -d studentcv` → `accepting connections`.
3. `http://127.0.0.1:5050` — вход, сервер `ksu-db` виден без ручной регистрации, `studentcv` открыт.
4. `alembic current` = `0001 (head)`; в pgAdmin видны 6 таблиц + тип `attendance_status`;
   `\dt` / `\d+ attendance_records` показывает UNIQUE и CHECK'и.
5. `alembic downgrade base` → `upgrade head` проходит без ошибок (миграции обратимы).
6. Дым-тест данных (SQL-консоль pgAdmin или `psql`):
   - вставка студента `01-ФИИтт-01` - ок; `01-фиитт-01` и `01-ФИтт-01` - ошибка CHECK;
   - вставка `attendance_records` со `status=LATE`, `delay_minutes=12` → ок;
   - `status=LATE` c `delay_minutes IS NULL` → ошибка CHECK;
   - **повтор той же пары тем же студентом → `UniqueViolation`**;
   - удаление студента каскадно снимает его `student_photos`.
7. `docker compose restart` → данные остались (volume работает). `docker compose down -v` → чистая БД;
   последний documented как «ядерная кнопка», не рутина.
8. `db.seeds` можно запустить дважды подряд без `IntegrityError` (идемпотентность).
9. `scripts/backup.ps1` → в `./backups/` появился файл `.dump`; после `down -v` + `up` +
   `scripts/restore.ps1` количество строк в `students` и `attendance_records` совпадает со снятым.
10. `docker compose -f compose.yaml -f compose.dist.yaml config` → в выводе **нет** сервисов `pgadmin4`
    и `backend`, у `db` нет `ports`; в `docker compose config` (dev) — оба есть, `db` слушает
    `127.0.0.1:5433`.

## 8. Риски и известные питфоллы этого окружения

| Риск | Проявление | Что делаем |
| --- | --- | --- |
| Сеть из-под песочницы | `docker pull` / `pip install` блокируются | команды с полным доступом, явное одобрение; заранее не считать это багом compose |
| Порты заняты на Windows | `Error 10048 / address already in use` | 5433 и 5050 вместо стандартных; проверка `netstat -ano` до старта |
| CRLF в init-скриптах | `/docker-entrypoint-initdb.d/*.sql` молча не исполняется, БД без расширений | `.gitattributes` → `*.sh text eol=lf`, `*.sql text eol=lf`; в скриптах без shebang |
| Кириллический regex | CHECK на группе не срабатывает или бракует валидные значения | UTF8 + `locale=C`, тесты §7.6, `Ё` в классе символов |
| Bind-mount PG data на Windows | падение кластера, `data directory has wrong ownership` | именованный volume `pgdata` |
| autogenerate и enum/CHECK | миграция «съедает» тип или констрейнт | ручная досмотрка `0001_init`, тесты §7.4 |
| Пул на мёртвой БД | backend висит после `restart db` | `pool_pre_ping=True`, `depends_on: service_healthy` |
| Требование №10 vs Docker | «локальный десктоп .exe, всё на ПК пользователя» конфликтует с контейнерным развёртыванием | **решено**: гибрид по слоям (§1.1) + переформулированный AC1. Слой данных от этого не зависит — engine строится по DSN |
| Docker Desktop: лицензия и ресурсы | Personal-тариф может не покрывать эксплуатацию в вузе; WSL2 + PG + CV-модель не влезают в 8 ГБ | fallback на Docker Engine / Podman в WSL2; проверить ТЗ вехи 4 по ОЗУ |
| PowerShell-скрипты | не-ASCII ломает парсинг | вспомогательные `.ps1` — только ASCII |
| Бинарный вывод через cmd | `pg_dump > file` и `type dump \| pg_restore` портят байты, `pg_restore` отвергает архив | дамп пишется **внутри** контейнера и копируется наружу через `docker compose cp`; заголовок `PGDMP` проверяется перед использованием |
| `docker compose cp` пишет прогресс в stderr | при `ErrorActionPreference='Stop'` скрипт падает на успешной операции | внутри скриптов stderr гасится (`$ErrorActionPreference='Continue'` на время вызова) |
| Кириллица через `cmd /c` | SQL с русскими значениями доходит до `psql` в битой кодировке | SQL-файл копируется в контейнер через `docker compose cp`, `psql` пишет результат в файл внутри контейнера, файл забирается обратно и читается как UTF-8 |
| `naming_convention` + явные имена | `ck_students_group_number_format` превращался в `ck_students_ck_students_group_number_format` | в миграции передаётся короткое имя (`group_number_format`), префикс добавляет конвенция |
| Двойное создание PG-enum | `DuplicateObjectError` при `alembic upgrade head` | тип создаёт хук `before_create` (`create_type=True`); вручную в миграции **не** создаём |

## 9. Открытые вопросы (вынести на обсуждение команды)

1. **Справочник времени пар (отложено по решению от 08.11).** В README `lessons` хранит
   `start_time/end_time` явно, а шаблон 7 пар описан отдельным списком — то же время дублируется в
   каждой строке и правится UPDATE'ом по всем. Альтернатива: таблица `lesson_slots (id, slot_number,
   start_time, end_time)` + `lessons.slot_id` FK, тогда расписание живёт в одном месте и требование №5
   читает слот напрямую. Стоимость обратного хода низкая: `create table lesson_slots` + `add column
   slot_id integer references …` + backfill по `start_time` — одна миграция, данные не теряются.
   Поэтому стартуем с README-варианта, решение не блокирует срез.
2. **Формулировка «1–5 фото»** (треб. №8) — **закрыто 10.11**: сервисная проверка
   (`app/services/photos.py`), а не триггер: CHECK по чужим строкам не выражается. Нижняя
   граница предупреждает, но не блокирует удаление последнего («разрешить и предупреждать»).
3. **Поставка под Windows (треб. №10) — технически закрыто, осталась юридическая проверка.**
   Решение: гибрид (§1.1) + переформулированный AC1, внесённый в `Реестр требований.md`. Открытым
   остаётся только: (а) покрывает ли Personal-тариф Docker Desktop внутреннюю эксплуатацию в вузе —
   спросить юристов; (б) проходит ли целевой образ ПК по WSL2/виртуализации/ОЗУ. Влияет на то, можно
   ли держать `pgdata` в volume или нужен файловый каталог рядом с приложением.
4. **Минимальный набор полей `teachers`** для авторизации КГУ: хватит `login` + `password_hash`, или
   нужен `role`/привязка к подразделению? Уточнить у заказчика до слоя авторизации.
5. **`ABSENT` как строка или как отсутствие строки.** Сейчас принята вторая модель (запись создаётся
   по факту распознавания). Если отчёты требуют явные строки отсутствия — это меняет UNIQUE и логику
   формирования журнала, решать до слоя отчётов.
6. **Пароль pgAdmin в `servers.json`** в открытом виде — **решено**: pgAdmin исключён из поставки
   (`compose.dist.yaml` → `!reset null`), он инструментарий разработки, а не продукт. Для контура КГУ,
   если pgAdmin всё же понадобится на сервере разработки — server mode + мастер-пароль.
7. **Alembic в контуре поставки** — миграции выполняются стартовым сервисом или внешним релиз-процессом?
